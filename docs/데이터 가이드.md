# 데이터 저장 구조 및 DB 선택 기준

## 1. DB 선택: PostgreSQL 사용

본 프로젝트에서는 데이터 저장 및 분석용 DB로 **PostgreSQL**을 사용한다.

### PostgreSQL을 선택한 이유

본 서비스는 단순 CRUD 중심의 웹서비스가 아니라, 항공권 구매 타이밍 판단을 위해 여러 공공데이터를 수집·전처리·결합하고, 노선·공항·날짜 단위로 분석 피처를 생성하는 데이터 분석형 서비스에 가깝다.

따라서 다음과 같은 이유로 PostgreSQL이 적합하다.

| 구분 | 선택 이유 |
|---|---|
| 분석 쿼리 | 날짜별, 노선별, 공항별 집계 및 비교 쿼리에 적합 |
| 데이터 확장성 | 항공통계, 환율, 공휴일, 운항 정보 등 다양한 테이블을 관계형 구조로 관리 가능 |
| JSON 처리 | API 원천 응답이나 분석 로그를 JSON 형태로 저장 가능 |
| 공간 데이터 확장 | 향후 공항 위치, 노선 거리, 국가·도시 단위 분석 확장 시 PostGIS 활용 가능 |
| Python 연동 | pandas, SQLAlchemy, FastAPI, Streamlit과 연동이 용이 |
| 프로젝트 적합성 | 공공데이터 기반 분석 서비스 구조에 적합 |

### MySQL 대신 PostgreSQL을 선택한 이유

MySQL도 일반적인 웹서비스 개발에는 충분히 사용할 수 있다.  
그러나 본 프로젝트는 회원, 게시글, 주문과 같은 단순 트랜잭션 중심 서비스가 아니라, 여러 공공데이터를 결합하여 분석 피처를 만들고 Agent가 판단에 활용하는 구조이다.

따라서 복잡한 집계, 날짜 기반 분석, JSON 데이터 저장, 향후 공간 데이터 확장 가능성을 고려하면 PostgreSQL이 더 적합하다.

정리하면 다음과 같다.

| DB | 적합한 경우 | 본 프로젝트 적합도 |
|---|---|---|
| MySQL | 일반적인 웹서비스, CRUD 중심 서비스 | 가능은 하지만 우선순위 낮음 |
| PostgreSQL | 분석형 서비스, 복잡한 쿼리, JSON, 공간 데이터 확장 | 적합 |

본 프로젝트에서는 **PostgreSQL을 기본 DB로 사용**한다.

## 2. 데이터 저장 방식

본 프로젝트의 데이터는 크게 다음 세 단계로 구분하여 관리한다.

```text
1. 원천 데이터
2. 전처리 데이터
3. 분석용 피처 데이터
```

전체 흐름은 다음과 같다.

```text
공공데이터/API 수집
→ 원천 데이터 저장
→ 전처리
→ 분석용 피처 생성
→ PostgreSQL 저장
→ 앱/Agent가 조회
→ 사용자에게 분석 결과 제공
```

---

## 3. DB 저장 대상과 인메모리 처리 대상 구분

모든 데이터를 무조건 DB에 저장하지 않는다.  
재사용이 필요하거나 추적이 필요한 데이터는 DB에 저장하고, 사용자의 단일 요청에서만 필요한 임시 계산 결과는 인메모리에서 처리한다.

### 저장 기준

| 구분 | 저장 방식 | 기준 |
|---|---|---|
| 원천 데이터 | DB 또는 raw 파일 저장 | 재수집·검증·추적이 필요한 데이터 |
| 전처리 데이터 | DB 또는 processed 파일 저장 | 분석 피처 생성의 중간 산출물 |
| 분석용 피처 | DB 저장 | 앱과 Agent가 직접 조회하는 핵심 데이터 |
| Agent 판단 결과 | 인메모리 처리 | 요청마다 계산되는 임시 결과 |
| What-if 시뮬레이션 결과 | 인메모리 처리 | 화면 표시용 임시 비교 결과 |
| LLM 응답 결과 | 기본 인메모리, 필요 시 로그 저장 | 운영 로그가 필요한 경우만 DB 저장 |

## 4. DB에 저장할 데이터

DB에는 장기적으로 재사용하거나 분석 기준으로 활용할 데이터를 저장한다.

### 4-1. 원천 데이터 테이블

공공데이터/API에서 수집한 데이터를 원천 형태에 가깝게 저장한다.  
원천 데이터는 추후 재처리, 오류 검증, 수집 이력 확인을 위해 보관한다.

예상 테이블은 다음과 같다.

```text
raw_route_stats
raw_airport_stats
raw_airline_stats
raw_holiday_calendar
raw_exchange_rates
raw_flight_operations
```

### 테이블별 역할

| 테이블명 | 내용 |
|---|---|
| raw_route_stats | 노선별 항공통계 원천 데이터 |
| raw_airport_stats | 공항별 항공통계 원천 데이터 |
| raw_airline_stats | 항공사별 항공통계 원천 데이터 |
| raw_holiday_calendar | 공휴일·연휴 정보 원천 데이터 |
| raw_exchange_rates | 환율 정보 원천 데이터 |
| raw_flight_operations | 운항·지연·결항 정보 원천 데이터 |

---

## 5. 전처리 후 저장할 데이터

원천 데이터는 컬럼명, 날짜 형식, 공항 코드, 결측값 등이 서로 다를 수 있으므로 전처리 과정을 거친다.

전처리 단계에서는 다음 작업을 수행한다.

```text
- 컬럼명 표준화
- 날짜 형식 통일
- 공항 코드 정리
- 노선 코드 생성
- 결측값 처리
- 중복 제거
- 월별/일별 집계
- 증가율 계산
- 분석에 필요한 변수 생성
```

전처리 완료 데이터는 필요에 따라 다음과 같이 관리한다.

```text
data/processed/
또는
PostgreSQL processed_* 테이블
```

예상 테이블은 다음과 같다.

```text
processed_route_stats
processed_airport_stats
processed_exchange_rates
processed_holidays
processed_flight_operations
```

## 6. 최종 분석용 피처 테이블

앱과 Agent가 직접 사용하는 핵심 테이블은 `route_features`이다.

현재 MVP에서 사용 중인 `data/sample_route_features.csv`는 향후 PostgreSQL의 `route_features` 테이블로 전환한다.

### route_features 역할

`route_features`는 노선·출발일 단위로 항공권 구매 타이밍 판단에 필요한 변수를 모아둔 분석용 테이블이다.

Agent는 원천 데이터를 직접 조회하지 않고, 전처리가 끝난 `route_features`를 조회하여 위험도를 계산한다.

### route_features 예시 컬럼

| 컬럼명 | 설명 |
|---|---|
| route | 노선 코드 |
| departure_airport | 출발 공항 코드 |
| arrival_airport | 도착 공항 코드 |
| departure_date | 출발일 |
| passenger_growth_rate | 여객 수요 증가율 |
| flight_growth_rate | 운항편 증가율 |
| days_to_holiday | 공휴일/연휴까지 남은 일수 |
| holiday_name | 인접 공휴일/연휴명 |
| jpy_krw_change_rate | 엔화 환율 변화율 |
| delay_rate | 운항 지연율 |
| cancel_count | 결항 건수 |

### route_features 예시

```text
route, departure_airport, arrival_airport, departure_date, passenger_growth_rate, flight_growth_rate, days_to_holiday, holiday_name, jpy_krw_change_rate, delay_rate, cancel_count
ICN-NRT, ICN, NRT, 2026-09-25, 12.5, 2.1, 2, 추석 연휴, 3.4, 4.2, 0
```

## 7. 인메모리로 처리할 데이터

다음 데이터는 DB에 저장하지 않고, 앱 실행 중 메모리에서 계산 후 화면에 표시한다.

```text
- 사용자가 선택한 출발공항
- 사용자가 선택한 도착공항
- 사용자가 선택한 출발일
- Agent별 위험도 계산 결과
- 종합 위험도 점수
- What-if 일정 변경 시뮬레이션 결과
- 목적지 비교 시뮬레이션 결과
- 화면 표시용 DataFrame
```

### 인메모리 처리 이유

이 데이터들은 사용자의 요청마다 달라지는 임시 계산 결과이다.  
장기 저장이 필요하지 않고, 매번 DB에 저장하면 불필요한 로그가 과도하게 쌓일 수 있다.

따라서 기본적으로는 인메모리에서 처리하고, 필요한 경우에만 분석 로그로 저장한다.

---

## 8. 분석 로그 저장 여부

서비스 운영 단계에서는 사용자의 분석 요청과 결과를 저장할 수 있다.  
다만 MVP 단계에서는 필수는 아니다.

향후 사용자 행동 분석이나 서비스 개선이 필요할 경우 `analysis_logs` 테이블을 추가한다.

### analysis_logs 예시 컬럼

| 컬럼명 | 설명 |
|---|---|
| log_id | 분석 로그 ID |
| created_at | 분석 실행 시각 |
| departure_airport | 출발 공항 |
| arrival_airport | 도착 공항 |
| departure_date | 출발일 |
| risk_score | 종합 위험도 점수 |
| risk_level | 위험도 등급 |
| recommendation | 구매 판단 |
| result_json | Agent 분석 결과 JSON |

### 저장 목적

```text
- 사용자가 어떤 노선을 많이 분석하는지 확인
- 어떤 조건에서 위험도가 높게 나오는지 검토
- Agent 판단 로직 개선
- 서비스 사용성 분석
```

단, 개인정보나 민감한 사용자 입력은 저장하지 않는 것을 기본 원칙으로 한다.

## 9. 최종 저장 구조 요약

본 프로젝트의 최종 데이터 저장 구조는 다음과 같다.

```text
data/raw/
- 원천 CSV 또는 API 응답 백업

data/processed/
- 전처리 완료 CSV
- DB 적재 전 검증용 데이터

PostgreSQL
- raw_* 테이블
- processed_* 테이블
- route_features 테이블
- analysis_logs 테이블
```

앱과 Agent의 조회 흐름은 다음과 같다.

```text
사용자 입력
→ PostgreSQL route_features 조회
→ Agent 위험도 계산
→ What-if / 목적지 비교는 인메모리 계산
→ 사용자 화면에 결과 표시
```

## 10. 결론

본 프로젝트에서는 **PostgreSQL을 기본 DB로 사용**한다.

데이터 저장 기준은 다음과 같다.

```text
DB 저장:
- 공공데이터 원천
- 전처리 완료 데이터
- 최종 분석용 route_features
- 필요 시 분석 로그

인메모리 처리:
- 사용자 단일 요청
- Agent 계산 결과
- What-if 시뮬레이션 결과
- 목적지 비교 결과
- 화면 표시용 임시 데이터
```

즉, 장기적으로 재사용하고 관리해야 하는 데이터는 DB에 저장하고, 요청마다 달라지는 임시 계산 결과는 인메모리에서 처리한다.
